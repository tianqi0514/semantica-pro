# 第五步：加载采购合规正式本体

本步骤开始配置“模型层”，不再增加一笔新的采购业务数据。

前四步导入的是具体实例，例如：

```text
SUPPLIER-001 = 华星科技有限公司
BID-001      = 一份具体投标文件
```

第五步定义这些实例背后的通用模型，例如：

```text
Supplier       = 供应商是一类什么对象
Bid            = 投标文件是一类什么对象
hasRiskEvidence = 供应商可以关联监管通报
flags_supplier  = 审查结论可以标记风险供应商
```

## 要使用的文件

`5-采购合规本体.ttl`

这是 Turtle 格式的 OWL 本体，不要在普通“导入与导出”页面上传。

## 页面操作

1. 打开左侧“本体中心”。
2. 进入“本体管理”。
3. 点击“加载本体”。
4. 选择“文件上传”。
5. 选择 `5-采购合规本体.ttl`。
6. 点击“加载本体”。
7. 加载成功后回到本体管理列表。

## 上传后看什么

列表中应出现：

```text
采购合规审查本体
版本：1.0.0
```

在“本体搜索”中可以分别搜索：

```text
Supplier
PurchaseRequest
hasRiskEvidence
flags_supplier
```

点开 `Supplier`，应看到中文名称“供应商”；点开 `hasRiskEvidence`，应看到：

```text
domain：Supplier
range：RegulatoryNotice
```

含义是：`hasRiskEvidence` 关系的起点应该是供应商，终点应该是监管通报。

## 这一步配置了什么

本体文件正式定义了：

- 3 个上层分类：业务对象、参与方、管控对象；
- 8 个具体业务类：审查结论、采购申请、制度、材料、员工、投标、供应商、监管通报；
- 8 种对象关系；
- 5 个主要数据属性；
- 当前 JSON 简写与本体名称之间的对应说明。

例如：

```turtle
pc:Supplier a owl:Class ;
  rdfs:label "供应商"@zh ;
  pc:jsonType "supplier" .
```

表示当前 JSON 中的：

```json
"type": "supplier"
```

在业务语义上对应正式类 `pc:Supplier`。

## 与现有实例数据的关系

加载本体不会把 `SUPPLIER-001` 改名，也不会重新生成前四步的数据。本体类和业务实例会同时存在：

```text
pc:Supplier  —— 通用定义
SUPPLIER-001 —— 具体供应商实例
```

本步骤先完成模型定义和展示。下一步再配置约束并检查实例数据是否符合模型。
